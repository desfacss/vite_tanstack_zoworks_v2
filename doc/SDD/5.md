You've hit on a crucial insight: **your app is config-driven**, so the traditional separation of frontend/backend specs creates dangerous duplication. The real source of truth is already in your Supabase tables (`core.forms`, `core.view_configs`, etc.). Your contracts should **reference** these tables, not duplicate them.

## The "Single SDD" Approach for Config-Driven Apps

Yes, organize as **one SDD folder** with layered content, but the layers are different from typical apps:

```
your-workspace/
├── backend-supabase/          # Your existing backend
├── frontend-react/            # Your existing frontend  
└── sdd/                       # SINGLE source of truth
    ├── 00_CONSTITUTION.md     # Immutable rules
    ├── 01_DOMAIN_MODELS.md    # Business entities & relationships
    ├── 02_CONFIG_STATE.md     # What's IN Supabase tables (referenced, not duplicated)
    ├── 03_BACKEND_CONTRACTS.md # RPCs, Edge Functions, SQL tests
    ├── 04_FRONTEND_CONTRACTS.md # Routes, form names, registry entries
    ├── 05_INTEGRATION_FLOWS.md # End-to-end stories
    └── 06_TEST_ORDERS.md      # Which tests run when (critical for config-driven)
```

## The Key Difference: Your Config is the Source

Unlike normal apps where code is source of truth, **your Supabase config tables ARE the running spec**. Your SDD files should:

1. **Reference** config table names, not duplicate schema
2. **Define validation rules** for what can be inserted
3. **Provide test cases** that verify config + code together

### Example: `02_CONFIG_STATE.md`


## How Agents Use This Structure

### When running agent in `backend-supabase/`:

The agent reads from `sdd/03_BACKEND_CONTRACTS.md` and `sdd/06_TEST_ORDERS.md` Phase 1-2:

```markdown
## Agent Instructions for Backend (in .cursorrules)
When implementing a new RPC:
1. Read `sdd/03_BACKEND_CONTRACTS.md` for naming conventions
2. Implement RPC in Supabase migration
3. Write SQL test in `sdd/06_TEST_ORDERS.md` Phase 1.2
4. Run test: `psql -f test.sql`
5. Mark test as [PASSED] in the SDD file
```

### When running agent in `frontend-react/`:

The agent reads `sdd/04_FRONTEND_CONTRACTS.md` but **references** `sdd/06_TEST_ORDERS.md` Phase 3-4:

```markdown
## Agent Instructions for Frontend (in .cursorrules)
Before implementing any React component:
1. Verify backend RPC exists (check Phase 1.2 tests passed)
2. Verify form config exists in core.forms (run Phase 2.2 SQL)
3. Then implement component following `sdd/04_FRONTEND_CONTRACTS.md`
4. Run UI test from `sdd/06_TEST_ORDERS.md` Phase 3.x
```

## Change Management Without Duplication

When you need to modify something:

### Example: Add a new field to CRM Account form

**OLD WAY** (duplication):
- Change `core.forms` data_schema
- Update frontend types
- Update documentation

**NEW WAY** (config-driven):
1. **Change only the SDD test expectation**:
```markdown
# In sdd/06_TEST_ORDERS.md Phase 2.1
-  '{"type":"object","properties":{"name":{"type":"string"}}}'::jsonb,
+  '{"type":"object","properties":{"name":{"type":"string"},"tax_id":{"type":"string"}}}'::jsonb,
```

2. **Agent reads the test change** and:
   - Updates `core.forms` via RPC or SQL migration
   - Runs Phase 2.2 verification
   - Frontend automatically works (DynamicForm picks up new schema)

## Why This Works Better

| Traditional SDD | Your Config-Driven SDD |
| :--- | :--- |
| Duplicates schema in code | **References schema in Supabase tables** |
| Tests verify code matches spec | **Tests verify config + code together** |
| Change requires code deployment | **Change updates config, code unchanged** |
| Separate BE/FE specs | **Mixed integration specs** |
| Manual test order | **SDD defines test phases** |

## Final Recommendation

Create **one `sdd/` folder** with:
- **Backend-first tests** (SQL + curl) that validate schema and RPCs
- **Config state documentation** that references `core.forms`, `core.view_configs`
- **Mixed integration flows** that show BE + CONFIG + FE working together
- **Test order that starts with SQL, ends with E2E**

The agents read from the **same SDD folder** whether they're in backend or frontend project. The only difference is which phase of `06_TEST_ORDERS.md` they focus on.

This matches your config-driven reality: **Supabase is the source, SDD is the validator, code is the executor**.
