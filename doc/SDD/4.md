Based on the two articles you shared, I've analyzed the core principles of Spec-Driven Development (SDD) and synthesized them into a practical, **single-source-of-truth folder structure** for your config-driven ERP system.

This structure is designed to be **spec-anchored**, as described in the Martin Fowler article, meaning the specifications evolve with your code across all environments (Supabase, Cloudflare Workers, Google Run). It acts as the central source for agents to both **develop new features from specs** and **reverse-engineer specs from existing code**.

Here is the proposed folder structure and the rationale behind its design, directly informed by your references.

### Core SDD Principles Applied to Your Structure

| SDD Principle (from articles) | Implementation in Your Folder Structure |
| :--- | :--- |
| **Spec-First & Spec-Anchored** (Fowler) | The `SDD/` folder is the master source. Every code change starts with a spec update, and the spec is maintained alongside the code for evolution. |
| **Immutable Constitution** (spec-kit) | `01_CONSTITUTION.md` defines non-negotiable rules for RLS, RPCs, dynamic forms, etc., that all agents must follow. |
| **Memory Bank / Steering** (Kiro, spec-kit) | The `00_INDEX.md` and module-level `00_MODULE_INDEX.md` files act as the navigation and dependency map for agents. |
| **Structured, Testable Specs** (Tessl) | Each module has a `01_BUSINESS_RULES.md` (with Gherkin-like rules) and `06_TEST_CASES.md` (with phased, executable tests). |
| **Separating Functional & Technical** (Fowler) | `02_DOMAIN_MODELS.md` and module `01_BUSINESS_RULES.md` are functional. `03_BACKEND_CONTRACTS.md`, `04_FRONTEND_CONTRACTS.md`, and `skills/` are technical. |
| **Change Management** (spec-anchored) | Every module has `07_CHANGE_LOG.md` to track the "OLD vs NEW" state of a spec, exactly as you requested. |

### How This Structure Enables Your Key Needs

#### 1. Developing Specs from Existing Code (Reverse Engineering)
Your existing Supabase schemas, RPCs (`onboard_*`), Edge Functions (`invite_users`), and React components (`InviteUserModal`) are the "golden source" of truth. An agent can be tasked to populate this `SDD/` folder by:
- **Reading** your database schemas and RPC definitions to write `modules/identity/02_CONFIG_STATE.md` and `03_BACKEND_CONTRACTS.md`.
- **Analyzing** `InviteUserModal.tsx` to generate `modules/identity/04_FRONTEND_CONTRACTS.md` and the `useInviteUser` hook specification.
- **Extracting** business rules from `onboard_invite_user_to_org` SQL logic into `modules/identity/01_BUSINESS_RULES.md` (Rules 1-4).
- **Converting** your manual test scripts into the structured `06_TEST_CASES.md` format.

#### 2. Structuring for a Config-Driven ERP
This design directly supports your "config over code" philosophy:
- **`modules/forms-engine/`** : Holds the specs for all dynamic forms in `core.forms`. A change here means updating a spec, not touching frontend code.
- **`01_CONSTITUTION.md`** : Codifies your "Dynamic Forms for ALL CRUD" rule, forcing agents to propose config changes first.
- **`04_FRONTEND_CONTRACTS.md`** : Documents the exact contract for registering a **custom component** (like `ClientBespokeForm`) in `src/core/registry.ts`, ensuring it's a deliberate, spec-driven exception.

#### 3. Providing a Single Source of Truth for Disparate Deployments
Your system spans **Supabase (main backend)** , **Cloudflare Workers**, and **Google Run**. This structure provides a unified view:
- **`modules/identity/03_BACKEND_CONTRACTS.md`** : Will contain separate sections for Supabase RPCs, Edge Functions (`supabase/functions/invite_users`), and potentially a section for a related Cloudflare Worker.
- **`features/tenant-onboarding/02_TECHNICAL_DESIGN.md`** : Would include a sequence diagram showing the interaction between your React frontend, the `invite_users` Edge Function (Supabase), and the `onboard_promote_to_tenant` RPC.
- **Agent Tasking** : A task like `TASK-BE-003: Deploy invite_users Edge Function` in `04_IMPLEMENTATION_TASKS.md` clearly tells an agent where to operate (`supabase/functions/invite_users/`).

### Agent Workflow Using This Structure

When an agent (Claude Code, Cursor, etc.) is assigned a task, its workflow is strictly defined:

1.  **Read Constitution & Index** : Load `01_CONSTITUTION.md` and `00_INDEX.md` into its context for global rules.
2.  **Locate Feature Spec** : Navigate to `features/[feature-name]/`. For `tenant-onboarding`, it reads `01_ACCEPTANCE_CRITERIA.md` to understand the *what* and `02_TECHNICAL_DESIGN.md` for the *how*.
3.  **Consult Module Contracts** : For implementation, it reads the specific module contracts. To build `ApproveOrgModal`, it checks `modules/identity/03_BACKEND_CONTRACTS.md` (for the `onboard_promote_to_tenant` RPC) and `04_FRONTEND_CONTRACTS.md` (for component patterns).
4.  **Execute & Test** : It follows `04_IMPLEMENTATION_TASKS.md` (e.g., `TASK-FE-003`) and verifies against the relevant tests in `modules/identity/06_TEST_CASES.md` (e.g., TEST-005, TEST-012).
5.  **Update Spec** : After implementation, it must update the spec, primarily documenting changes in `07_CHANGE_LOG.md` using the **OLD vs NEW** format, embodying the **spec-anchored** principle.

This structure provides a robust, actionable framework that turns your existing codebase into a living, spec-driven ecosystem, perfectly aligned with the advanced practices outlined in your references.
